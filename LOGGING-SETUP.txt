Create the logging directory and grant permission
Run an elevated PowerShell window on the IIS server. Replace these TWO example
values with the actual site's physical directory and exact IIS app pool name:

  $chatbotSitePath = 'D:\Sites\MedicountChatbot\releases\fixed-2026-11-05'
  $chatbotAppPool = 'YOUR_ACTUAL_IIS_APP_POOL_NAME'
  $chatbotLogPath = Join-Path $chatbotSitePath 'logs'
  New-Item -ItemType Directory -Path $chatbotLogPath -Force | Out-Null
  icacls $chatbotLogPath /grant "IIS AppPool\${chatbotAppPool}:(OI)(CI)M"

Grant Modify only on logs; the application files need Read & Execute. If the pool
runs as a custom domain service account, grant that identity instead. Restrict
configuration and log access to authorized administrators/service identities.
Do not place logs in wwwroot. The application refuses that configuration.

Where to look
Application: <site directory>\logs\application\application-*.jsonl
  JSON Lines: one event per line, timestamps in UTC, build=1.0.1.0.
  Covers startup, each known HTTP route, session/form/conversation processing,
  SQL connection and query stages, verification outcomes, insurance transaction
  stages, billing requests, SMTP/Graph, outbox delivery, retries and maintenance.
  Works independently of SQL, so database outages are still recorded.

IIS startup: <site directory>\logs\startup\stdout_*.log
  Captures process startup failures and console/stderr. stdoutLogEnabled=true
  in the supplied file is temporary for troubleshooting. Set it to false after
  startup is healthy; application logs continue. IIS stdout files do NOT rotate.
  Do not enable broad IIS module TRACE or HTTP body logging for patient traffic.

Browser: Developer Tools > Console and Network
  Safe console warnings contain only the action, HTTP status/network_error and
  a validated trace ID. Responses include X-Trace-Id. Service-outage messages
  display Reference: <32-character ID>. Normal identity mismatches do not display
  an operational error reference. Browser developer tools can still show form
  request bodies; do not share whole HAR files or screenshots containing PHI.

Find all events for the browser's reference
On the IIS server, replace the path and trace ID below:

  $chatbotLogPath = 'D:\YOUR_SITE_DIRECTORY\logs\application'
  $chatbotTrace = 'PASTE_THE_32_CHARACTER_REFERENCE'
  Get-ChildItem -LiteralPath $chatbotLogPath -Filter 'application-*.jsonl' |
    Get-Content |
    ConvertFrom-Json |
    Where-Object { $_.traceId -eq $chatbotTrace } |
    Select-Object timestampUtc, operation, outcome, elapsedMs, statusCode,
                  exceptionType, sqlNumber, sqlState, socketError

Read the first failing stage
  configuration.hash_secret / missing_or_short or placeholder_not_replaced:
    Supply the persistent hash secret in web.config.
  startup.configuration / failed:
    Check mode, origins, store, hash secret and connection-string syntax.
  startup.flow_catalog / failed:
    Confirm the complete flows directory was uploaded with the published app.
  http.origin / rejected:
    Check PUBLIC_ORIGIN and PARENT_ORIGINS; no path/trailing slash is allowed.
  sql.store.create.connection_open / failed:
    Chat session could not reach/authenticate to SQL; inspect sqlNumber/socketError.
  sql.patient_verification.connection_open / failed:
    SQL network, credentials, database access or TLS failed before the procedure.
  sql.patient_verification.query / failed:
    Connection succeeded; check procedure permissions/contract and query timeout.
  sql.patient_verification / no_match:
    Query completed without a matching patient. Check the synthetic record and
    actual procedure logic with the DBA; this is not a connectivity failure.
  sql.patient_verification / match:
    SQL verification succeeded. Inspect later stages if the selected action fails.
  sql.insurance.* / failed:
    Check the insurance procedure, required key table, grants and transaction.
  billing.http / disabled or mail.send / disabled:
    Expected while the corresponding integration is disabled.
  DIAGNOSTIC_LOG_WRITE_FAILED in stdout:
    Check app-pool Modify access to logs and available disk space.

If IIS rejects web.config before the managed application starts, there may be no
application log or trace ID. Inspect IIS's status/substatus and Event Viewer >
Windows Logs > Application. Validate XML and the installed .NET 10 Hosting Bundle.

Retention and sensitive data
Application logs rotate at 10 MiB, retaining up to 14 matching files (roughly
140 MiB) when the process has delete permission. The limits are configurable:
  DIAGNOSTICS_MAX_FILE_BYTES=10485760
  DIAGNOSTICS_MAX_FILES=14
  DIAGNOSTICS_ENABLED=true
Logs contain fixed operation/outcome codes, server-generated per-request IDs,
timings, HTTP status, exception type and numeric SQL/socket error metadata.
They do not contain names, DOBs, account/member IDs, contact details, chat text,
form bodies, SQL text/parameters, passwords, connection strings, tokens, session
IDs, account hashes, raw exception messages/stacks, URLs or query strings.
Existing application data in SQL is separate from this diagnostic logging.
